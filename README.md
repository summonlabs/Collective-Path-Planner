# Collective Path Planner

Open-source, vendor-neutral C++20 planner for mapping collective communication
structures onto generation-bound physical network fabrics under topology,
failure-domain, bandwidth, latency, congestion and policy constraints.

**1.0.0**

## What this is

Given a collective communication structure (a ring, a tree, hierarchical groups,
pairwise exchanges, an all-to-all edge set) and the current physical fabric, the
planner answers one question:

> Which deterministic set of paths and stages should carry this collective, and
> why is that mapping valid under the exact topology, failure-domain,
> capacity-evidence and policy generations now in force?

It answers with a **plan**: a generation-bound, content-addressed, replayable
record of physical paths, per-stage structure, proposed capacity allocations and
the evidence each path relied on.

## What this is not

A plan is a **candidate** until an adjacent authority validates and commits it.
This library does not own, and does not implement:

* collective algorithm execution - it chooses paths, it never moves data;
* general topology discovery - the fabric graph is supplied, never inferred;
* route installation or switch programming;
* traffic admission, bandwidth brokerage or reservation;
* congestion control - congestion enters only as a cost term derived from
  supplied evidence;
* workload scheduling.

It never opens a connection to a fabric element, never reads a device and never
mutates its inputs. Nothing in it claims that a plan is in effect.

## Proof labels

Every capability exercised by this repository is labelled:

| Label | Meaning here |
| --- | --- |
| **REAL** | Genuine operating-system processes, genuine loopback TCP, genuine files and genuine crash/restart. The transport, the coordinator, the durable store and the CLI are proven this way. |
| **SYNTHETIC** | Every network fabric, capacity and latency figure used anywhere in the tests, examples and this document. They are generated by models in this repository. No device, RDMA, SmartNIC/DPU, NVLink, InfiniBand, RoCE or programmable switch was measured. |
| **UNSUPPORTED** | Validation against physical network hardware. Not claimed. |

## Build

Requirements: CMake 3.20 or newer and a C++20 compiler. MSVC 19.40+ and
GCC 12+/Clang 15+ are the supported toolchains. There are no third-party
dependencies.

```sh
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release
```

CMake options:

| Option | Default | Meaning |
| --- | --- | --- |
| `CPATH_BUILD_TESTS` | ON when top level | Build the nine test suites |
| `CPATH_BUILD_TOOLS` | ON when top level | Build `cpath` and `cpathd` |
| `CPATH_BUILD_EXAMPLES` | ON when top level | Build the three examples |
| `CPATH_WARNINGS_AS_ERRORS` | ON | Zero first-party warnings, enforced |
| `CPATH_ENABLE_SANITIZERS` | OFF | AddressSanitizer + UndefinedBehaviorSanitizer |

Warnings are applied with a CMake function, not an exported interface library, so
an installed package never imposes this project's warning policy on a consumer.

## Quick start

```sh
cpath validate  --request fabric.cppt
cpath digest    --request fabric.cppt
cpath plan      --request fabric.cppt --out plan.cppb --text
cpath explain   --plan plan.cppb --request fabric.cppt
cpath compare   --a before.cppb --b after.cppb

cpath store put        --store ./store --request fabric.cppt
cpath store list       --store ./store
cpath store revalidate --store ./store --id <64 hex> --request fabric.cppt
cpath store verify     --store ./store

cpath rpc ping       --endpoint 127.0.0.1:9500
cpath rpc plan       --endpoint 127.0.0.1:9500 --request fabric.cppt --explain
cpath rpc shutdown   --endpoint 127.0.0.1:9500 --epoch 3
```

Exit codes are a contract: `0` success, `1` usage, `2` rejected input,
`3` planning refused, `4` persistence failure, `5` service failure,
`6` I/O failure.

The coordinator:

```sh
cpathd --bind 127.0.0.1 --port 9500 --store ./store --port-file ./port
```

`--port 0` selects an ephemeral port and `--port-file` publishes the bound port once
listening.

## The request DSL

The only text input the library accepts is a strict, line-oriented format. Full
reference: `docs/DSL.md`.

```
cpath-request 1
plan-generation 1
topology-generation 21
failure-domain-generation 4
capacity-evidence-generation 9
policy-generation 2

[collective]
id=demo-ring kind=ring demand=1000

[groups]
g0 level=0 pattern=ring members=p0,p1,p2,p3

[domains]
SITE kind=site
RACK-A kind=rack parent=SITE

[nodes]
n0 site=SITE rack=RACK-A host=HOST-0 device=0 tier=LEAF

[edges]
a0 from=n0 to=s0 capacity=25000 latency=100 tier=LEAF domain=HOST-0 evidence=synthetic

[bindings]
p0 node=n0

[policy]
max-hops=4
paths-per-logical-edge=1
disjointness=none
```

The reader treats every byte as untrusted: unknown sections and keys, duplicate
identifiers and sections, repeated keys on one line, malformed and out-of-range
numbers, over-long lines, an oversized input and trailing content are all refused
with a specific `ErrorCode` and a line number.

## The public API

```cpp
#include <cpath/dsl.hpp>
#include <cpath/planner.hpp>
#include <cpath/explain.hpp>

auto request = cpath::parse_request_text(text);      // Result<PlanningRequest>
if (!request) { /* request.status(): ErrorCode + detail */ }

cpath::PlanningOutcome outcome = cpath::plan_collective(request.value());
if (!outcome.ok()) {
  // A denial is terminal: no partial plan is ever returned beside it.
  // outcome.denials carries the code, the conflict class, the logical edge,
  // the participant and a bounded witness set.
}

const cpath::Plan& plan = *outcome.plan;
cpath::Status proof = cpath::validate_plan(plan, request.value());
```

| Header | Contents |
| --- | --- |

| `cpath/fabric.hpp` | `FabricSpec` -> `FabricGraph`, `Node`, `Edge`, `FailureDomain`, `EvidenceClass`, `DomainKind` |
| `cpath/collective.hpp` | `CollectiveSpec` -> `Collective`, groups, patterns, ring/tree/pairwise/all-to-all derivation |
| `cpath/policy.hpp` | hop limit, paths per logical edge, disjointness, domain diversity, evidence floor, weights, cost ceiling, forbidden sets, search budget |
| `cpath/request.hpp` | `RequestSpec` -> `PlanningRequest`, endpoint bindings, canonical digest |
| `cpath/plan.hpp` | `Plan`, `PathPlan`, `Hop`, `Stage`, `Allocation`, `validate_plan`, `assess_freshness` |
| `cpath/planner.hpp` | `plan_collective`, `find_path`, `PlanningOutcome`, `DenialDetail`, `ConflictKind` |
| `cpath/explain.hpp` | `explain_plan`, `explain_denials`, `render_plan_json`, `compare_plans` |
| `cpath/persistence.hpp` | `PlanStore`, `StoredPlanSummary`, `RevalidationResult`, record codec |
| `cpath/wire.hpp` | frame codec and every typed payload codec |
| `cpath/server.hpp` | `Coordinator` and `ServiceClient` |

Every fallible entry point returns `Status` or `Result<T>` carrying a stable
`ErrorCode`. No exception escapes a public function.

## What a plan contains

* its identity, which is the SHA-256 of the canonical request encoding;
* the five generations it was produced from;
* one or more stages (a flat collective has one; a hierarchical collective has
  one per declared level);
* the physical paths, each with its hops, cost, bottleneck and failure-domain
  signature;
* the weakest evidence class any path relied on;
* the capacity the plan would consume per physical edge - explicitly a proposal,
  not a reservation.

## Planning contract (summary)

The planner solves one declared problem class and is explicit about what it can
prove. The full statement is in `docs/DESIGN.md` section 9; the headline
properties are:

* **Never a false infeasibility.** `DenialKind::kProvenInfeasible` is emitted only
  when infeasibility was actually proven, for all constraints at once - by
  reachability, an exact minimum-hop distance, a max-flow bound, an exhaustive
  path set, or an exhaustive assignment search. Anything else is
  `DenialKind::kSearchLimitReached`, which is INDETERMINATE and makes no claim
  about existence.
* **Simple paths only.** No physical node and no physical edge appears twice in
  a path.
* **A deterministic, globally coherent objective.** Hard constraints first, then
  total cost, then sibling domain conflicts, then the largest single path cost,
  then capacity headroom, then a canonical tie-break. The same total order is
  used for partial comparisons, so the result never depends on container
  iteration, hash order, thread scheduling or candidate discovery order.
  Identical canonical requests produce byte-identical plans.
* **Global capacity decisions.** Candidate generation for a logical edge never
  depends on this request's other commitments, and the chosen sets are resolved
  together under the whole-request capacity constraint, so adding usable
  unconstrained fabric resources cannot withdraw a feasible mapping.

## Authority rules

* A plan binds all five generations. `assess_freshness` classifies it as
  `current` or as stale in exactly one dimension, and
  `describe_freshness` maps each classification to its own `ErrorCode`.
* Replanning under identical canonical inputs is deterministic: byte-identical
  plans, not merely equivalent ones.
* Impossible mappings are refused with a precise reason and **no partial plan**.
  Where the reason can be certified it is: an unsatisfiable disjointness
  requirement is reported with the exact upper bound a unit-capacity max-flow
  proves the fabric admits.
* Failure-domain independence is judged on the domains a path adds beyond its two
  endpoint attachment domains. Every sibling path necessarily sits in the source
  and destination domains, so those carry no discriminating information; two
  edge-disjoint routes that both transit the same pod are genuinely refused under
  required pod diversity.
* Zero capacity is never treated as capacity, `UNKNOWN` evidence is never
  upgraded, and a plan built on anything weaker than measured evidence says so.
* A store record is written under an epoch and an incarnation. Opening a store
  advances both, so a restarted process cannot resurrect authority held by its
  predecessor, and a reopened record is reported unverified until it is
  revalidated against a live request.

## Protocol

Frames are a 56-byte header, the payload, and a 32-byte SHA-256 over both. The
header carries a magic, a protocol version, a frame type, a strictly increasing
sequence number, the coordinator epoch, the payload length, a CRC-32 over the
header, the session identity the coordinator assigned, a request identity and two
reserved words. Full layout: `include/cpath/wire.hpp`.

* Every payload decoder is bounded and rejects trailing bytes.
* A frame that fails to decode closes its session.
* A protocol misuse on a well-formed frame is answered with a deterministic error
  frame and leaves the session usable.
* Sequence numbers advance strictly; a repeat is refused as a replay.
* Identity comes from the session envelope, never from a client-supplied field.
* Shutdown is driven by a per-session loopback wake-up socket, not by a timeout,
  so no protocol decision depends on an interval.

## Tests

Eleven suites, each a separate executable and a separate CTest entry, so a
failure localises to one proof surface:

| Suite | What it proves |
| --- | --- |
| `unit` | identities, canonical encoding, digests, fabric and collective validation, policy validation, DSL round-trips, freshness classification, plan comparison |
| `integration` | the whole public pipeline: text -> request -> plan -> validation -> rendering -> record round-trip, determinism, canonical equivalence, staleness |
| `property` | seeded randomized topologies with reproduction; every promised plan invariant re-checked after each randomized step |
| `algorithm` | algorithmic adversarial families: cheapest-first traps, locally-expensive-but-globally-necessary routes, candidate-pool truncation traps, cyclic graphs that tempt walk generation, symmetric ties, parallel links, bottleneck cuts, domain traps, long narrow graphs at the hop bound, additional irrelevant versus additional beneficial edges, canonical order independence, saturated cost arithmetic |
| `reference` | differential testing against a deliberately slow exact reference solver on bounded randomized instances: production plans are valid, proven infeasibility is sound, a reference solution always yields either a production plan or an explicit INDETERMINATE result, and claimed optimality matches the reference objective |
| `adversarial` | truncation and single-byte mutation at every offset, hostile documents, discontinuous, asymmetric, oversubscribed, duplicate-link, zero-capacity, cyclic-domain, stale-generation and huge-cost fabrics, search-budget exhaustion |
| `persistence` | record codec rejections, store lifecycle, restart fencing, revalidation classification, bounded growth, on-disk corruption, torn tails, erase and bounds |
| `protocol` | frame and payload codecs, every rejection code, never-crash inputs, and a real loopback TCP session against a live coordinator |
| `concurrency` | repeated start/stop, parallel clients behind a barrier, session limits, shutdown with live clients, self-initiated shutdown, cancelled handshakes, accounting closure |
| `multiprocess` | real `cpathd` and `cpath` processes over loopback TCP, an abrupt kill, restart with epoch and incarnation advancement, stale replay refusal, corrupt frames from a raw socket |
| `scale` | bounded planner work on large fabrics, growth ratios that expose accidental quadratic behaviour, saturation instead of wraparound |

Run them plainly - there is no timeout anywhere, in the framework or in CTest,
because a hang is a defect to diagnose rather than to mask:

```sh
ctest --test-dir build/release --output-on-failure
# or individually, with a fixed seed for reproduction
./build/release/tests/cpath_tests_property --seed=7 --verbose
```

A randomized failure prints the seed that produced it. 166 tests are registered
across the eleven suites (unit 47, adversarial 25, protocol 21, algorithm 18,
persistence 11, integration 9, property 8, concurrency 8, multiprocess 8,
reference 6, scale 5), and the whole run takes about 10 seconds in Release.

The reference suite alone drives 3,200 bounded randomized instances through both
the production planner and the exact reference solver, and the property suite
runs 2,500 seeded randomized iterations across ten families.

Every configuration is exercised before a release: a Release build, a Debug
build, and a build with AddressSanitizer and UndefinedBehaviorSanitizer enabled.
All twelve CTest entries - the nine suites plus the three examples - pass in each
of the three. The suite is also run against an installed package from a clean
prefix, and from a fresh clone of the pushed commit.

AddressSanitizer found three stack-use-after-scope defects in the test harness
itself while this release was being hardened; the comparison macros now capture
their operands by value, and the sanitizer run is clean.

## Install and consume

```sh
cmake --install build/release --prefix /some/prefix
```

This installs the static library, every public header, both executables, the
LICENSE and a CMake package. An independent consumer then does:

```cmake
find_package(CollectivePathPlanner 1.0 CONFIG REQUIRED)
target_link_libraries(my_target PRIVATE CollectivePathPlanner::cpath)
```

`examples/consumer/` is exactly such a project: it is a separate CMake project
that does not add this repository as a subdirectory, links only what was
installed, and proves the full pipeline - plan, commit, reopen, revalidate.

```sh
cmake -S examples/consumer -B build/consumer -DCMAKE_PREFIX_PATH=/some/prefix
cmake --build build/consumer
./build/consumer/cpath_consumer
```

## Limitations actually observed

* No physical hardware was exercised. Every fabric in the tests and examples is
  SYNTHETIC, and no path here is evidence about a real network.
* **What a denial means.** Every denial carries a `DenialKind`.
  `kProvenInfeasible` means no mapping exists and the planner proved it, from
  reachability, an exact minimum-hop distance, a max-flow bound, an exhaustive
  path set or an exhaustive assignment search. `kSearchLimitReached` means the
  search stopped at one of the declared bounds and the result is INDETERMINATE -
  it is never a claim that no mapping exists. `kInvalidRequest` and
  `kStaleInput` mean the request itself was unusable.
* **What is not proven optimal.** `PlanningOutcome::optimal` is true only when
  every logical edge's feasible path set was enumerated in full within
  `max_exhaustive_paths` and the k-subset and global assignment searches both
  ran to exhaustion. When it is false the plan is valid, deterministic and
  byte-identical for identical inputs, but a better mapping may exist outside the
  search bounds. Reaching a bound costs proof strength, never feasibility: the
  heuristic pool still produces a plan.
* **Simple paths.** Every emitted path is a simple path; no physical node and no
  physical edge appears twice. This is guaranteed by the search order, checked
  when a candidate is materialised, and re-derived independently by
  `validate_plan`.
* **Global capacity, not greedy commitment.** A logical edge's candidates are
  generated against the fabric's spare capacity only, never against this
  request's own earlier commitments. The chosen sets are then checked together,
  and a conflicting assignment is resolved by searching the per-logical-edge
  alternatives under the whole-request capacity constraint. Adding usable
  unconstrained fabric resources therefore cannot turn a feasible request into an
  infeasibility claim.
* A plan proposes capacity. It does not reserve it, and nothing here verifies
  that the proposal was ever admitted.
* Addresses are literal IPv4 or `localhost`. The transport is deliberately
  loopback-scoped and does not use a resolver.
* The store is single-writer: one process holds a store directory open at a time.
  It is not a distributed store, and the meta file is not a consensus log.
